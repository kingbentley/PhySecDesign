## Already confirmed acceptance obligations

OQ-9 must quantify the following without reopening their behavior:

- **NFR-1 / FR-22/34:** stable identities and relationships across saves, revisions, restore, export/import, replacement, archive and reopening; fixed evidence and historical packages do not mutate.
- **NFR-2 / FR-2/21/31/42:** Saved means acknowledged durable shared records **and associated attachments**, surviving browser closure and ordinary service restart. Connected browsers see saved changes within a few seconds. Independent edits/evidence coexist, retries are duplicate-safe, same-item conflicts preserve pending input, and guarded own-session undo cannot erase others' work. Exact seconds, transport and backup targets are still open. No browser-close recovery of unsaved input or durable offline capture is promised.
- **NFR-3:** designer/field use on phones, tablets and laptops; readable/labeled controls, keyboard access where applicable and non-color-only status. Browser/OS/device/accessibility acceptance matrix remains open.
- **NFR-4:** bounded analysis, visible unsupported inputs/sampling/effective resolution, usable import/analysis/export controls. Representative sizes and response times remain open.
- **NFR-5:** hosted HTTPS with server-enforced project-edit/revision-review scope, files included; revoked/out-of-scope links rejected; unverified names and sample/sanitized data. Hosting vendor is architecture work.
- **NFR-6 / FR-33/34:** readable, identified Design/Closeout packages; all floors by default; honest partial/evidence-limited output; explicit failed generation; retain exact issued/closeout PDF bytes and manifests for later download and backup. New generation is a new edition, not replacement of an earlier package. Two captioned photos/page is the accepted initial layout, not a total-photo cap.
- **SM-1–4 / A-2:** exercise all four journeys, solo/no-handoff and shared work, existing-site unknowns/retained assets/replacement, failure/retest, archives/restoration/reopening, visible unresolved work, preserved history and conflict/save failures. Fixture size is proposed, not accepted. FR-48 adds physical-asset versus optical-view versus stream counting; FR-51/52 add explicit port/run/segment/riser records that do not exist in today's schema.

## Recommended envelope considerations — proposals only

1. **Use a core journey fixture plus a separate upper-envelope fixture.** A modest core of about 50 physical assets across three floors, with a 100-asset/five-floor upper fixture, is a reasonable discussion starting point beyond historical 13-device QA. Count eligible optical views separately (for example ≤32 on one active floor), include multi-head and unassessed panoramic cases, and specify barriers/vertices/zones, runs/segments, explicit ports, evidence attempts, retained editions and bytes. These numbers are unmeasured proposals, not current support promises or a limit on approved feature scope. Dense-geometry rejection needs its own explicit graceful-failure case.
2. **Exercise at least two simultaneous editors and one reviewer.** Include independent camera edits, same-item conflicts, two evidence additions plus ambiguous retry, same-port claims, stale floor/device/archive changes, guarded undo and fixed snapshot creation. This proves the confirmed interaction model without pretending the current 20-reviewer cap proves 20 editors.
3. **Select real browser/device examples, not just widths.** A POC matrix could use a Windows laptop/desktop Chromium browser for complete design work, Safari on an iPhone/iPad and Chrome on an Android phone for the field path, with versions/devices recorded at acceptance. Use real photo picking/capture, touch, orientation and slow connection cases. Broader engine/version support is a separate choice. Check keyboard/tab/focus/error recovery, readable zoomed forms, announced save/conflict/result statuses and non-color-only outcomes; do not infer a formal accessibility conformance claim.
4. **Agree timed workloads and conditions before setting seconds.** Candidate targets for discussion: ordinary metadata save acknowledgement within 2 s; connected-browser propagation within 5 s; representative floor/analysis updates within 2–5 s; representative complete report within 30–60 s. Measure against named hardware, network, byte sizes and dataset, with UI progress/cancel/error behavior. Large-photo upload, cold PDF decoding, external geocoding/map delivery and all-floor evidence reports need separate measurements; the code's 350 ms/3.5 s/10 s values are not measured response commitments. Do not call a UI acknowledgement durable Saved before attachment association succeeds.
5. **Set separate attachment, retained-package and complete-backup budgets.** A photo count alone is unsafe: 50 maximum-sized current previews exceed today's 24 Mi-character aggregate, while 50 smaller previews may fit. Exact retained package files and lifecycle history now add data that current 100 MiB JSON was never built to hold. Even one near-80 MiB PDF plus 20 MiB current design would exceed that cap after JSON encoding/metadata, before revisions. Use a representative full-evidence manifest (two photos/page, repeated attempts, multiple editions) to choose page/byte/time budgets; do not silently omit required evidence to fit. Deduplicated assets/container design is architecture work, not a product mechanism selected here. Keep local original-PDF processing and captured-preview honesty.
6. **Separate ordinary persistence from recovery after loss.** Already confirmed: acknowledged records/attachments survive browser close and ordinary service restart; unsaved open-page input survives a failed request, with retry/current-version checks. Add an explicit controlled complete-backup restore exercise including devices/views/streams, ports/runs/risers, archives, issues, attempts, drawings/photos and byte-identical retained packages/manifests. Verify ID/relationship counts, representative content and package hashes; no access credential resurrection. Service/host loss, backup frequency/retention, maximum recoverable data loss and restore-time targets remain new OQ-9 decisions. A backup's existence or download button is not restore evidence.

No recommended number above is accepted or verified. The primary risk is treating today's permissive schema maxima as a supported operating envelope, or retaining today's small monolithic backup limits while promising substantially richer, immutable history and package retention.

## Parent candidate envelope check — 2026-11-17

The parent is considering, without acceptance: one property, two buildings, four plans, 100 physical devices, 40 assessed views total (at most 20/plan), 100 runs, 10 zones, three concurrent participants, 100 processed photos, 20 revisions and four retained exact packages; 50 MiB source PDF, 50 MiB aggregate processed plan/photo media, 100 pages/80 MiB per package and a 500 MiB complete desktop backup. This is a proposal, not implementation evidence or a recommendation already accepted by Kevin.

- **Backup arithmetic:** four final 80 MiB files +50 MiB media =370 MiB, leaving130 MiB of a 500 MiB cap for records/history/container overhead. This is a coherent bounded logical budget only if retained media/package bytes are not repeatedly duplicated into every full revision. Current JSON snapshots can repeat the media across 20 revisions plus current design, before base64 overhead; the current implementation does not meet that envelope. State that all subordinate maxima are subject to the aggregate cap.
- **Media arithmetic:** 100 current maximum-sized previews occupy70,000,000 encoded characters, above the existing24 ×1024²-character aggregate. Four processed plans at today's12 MiB image maximum would consume48 MiB of the proposed50 MiB, leaving2 MiB for all100 photos. The proposed counts can coexist only with smaller processed files and/or separate planned allocation. Bound total retained bytes, communicate per-file sizes and reject excess clearly; do not imply every file can simultaneously hit today's individual maximum.
- **Output arithmetic:** today's80 MiB limit measures accumulated JPEG page payload before PDF assembly, not final PDF size. A future80 MiB final-file cap needs its own exact-byte check. The100-page number has no current measured evidence. Count and byte limits must not silently truncate accepted evidence, overwrite an earlier exact package or delete protected history to make room; incomplete/partial choices remain explicit under FR-33/34.
- **Analysis complexity:** 20 assessed views/plan still needs a defined boundary/area and barrier-vertex envelope. Current hard work budgets can coarsen sampling well before10,000 cells, and the authored20-camera ×100-wall ×100-point case intentionally rejects with zero samples. Physical devices/views/streams are separate future counts; use stable view identities rather than the old physical-device ID when adapting analysis.
- **Concurrency:** three participants is a sensible small test cohort for the accepted conflict/retry/review scenarios, not a measured capacity claim. Current review serialization/polling and20 reviewer records do not establish shared editor performance.

State whether the timed completion includes the full floor result and all affected zones, or separately named operations, with pending results visibly pending. That prevents a selected-zone benchmark being mistaken for a whole-project refresh promise.
