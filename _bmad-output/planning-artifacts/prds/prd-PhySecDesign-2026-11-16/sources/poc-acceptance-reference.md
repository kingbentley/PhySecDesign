# POC acceptance reference

Research date: 2026-11-17 (America/Chicago).

Scope read before research: current source-index.md and .memlog.md. The POC covers a shared online property project from design through field records, commissioning and lifecycle history. Installers use phones, tablets and laptops; offline capture/synchronization is excluded. Autosave status, explicit shared-edit conflicts, duplicate-safe evidence retries, guarded undo, retained history and consistent saved export snapshots are already confirmed. OQ-9 acceptance limits remain a product decision. No application acceptance testing was performed for this note.

## Three official references

1. **Practical keyboard and visibility checks.** W3C WAI's Easy Checks covers keyboard operation, logical and visible focus, escaping controls without a keyboard trap, text contrast, resizing, labels and understandable errors. It explicitly describes these checks as a limited first review, not a complete accessibility assessment. [Easy Checks, Scope and Keyboard access and visual focus](https://www.w3.org/WAI/test-evaluate/preliminary/)
2. **Touch alternatives are distinct from keyboard alternatives.** W3C's dragging guidance explains that users need an equivalent single-pointer action without holding and dragging. Its examples include map-direction buttons and choosing two rectangle corners with separate taps. It notes that keyboard support alone does not satisfy the needs of touchscreen users. [Understanding Dragging Movements, Intent and Examples](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)
3. **Meaningful graphics and controls need visible contrast.** W3C's non-text contrast guidance discusses control identification, selected/focused states and graphics needed to understand content. It gives a 3:1 criterion against adjacent colours and cautions that thin, anti-aliased lines can remain hard to see. This is reference context; selecting a numeric POC target does not establish overall conformance. [Understanding Non-text Contrast, Intent and User Interface Components](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)

## Suggested acceptance application

These are proposed Site Studio checks inferred from the sources and confirmed product scope, not competitor benchmarks or an adopted WCAG checklist.

- **Exercise actual tasks with keyboard and visible focus:** locate/select a device through a list, edit its properties, enter field results, attach evidence, resolve a conflict, open/close dialogs and start an export. Verify logical focus movement and a way out of every control. Test the chosen workflow with text enlargement; keep controls, errors and save state usable.
- **Exercise touch alternatives:** on the selected phone/tablet, complete field records without hover-only actions or precision dragging. Where a tested map/drawing task uses drag, provide an equivalent suitable control, such as select-then-place, tap successive vertices, numeric position/size fields, or pan/zoom buttons. These are candidate interaction patterns, not a requirement to implement all of them. Verify keyboard and pointer alternatives separately.
- **Check important visual states on real plan backgrounds:** device selection, edit handles, focus, route/zone boundaries and status indicators must remain discernible. Use labels/icons or text summaries for consequential states such as Failed, Unassessed, Unsaved and Conflict. Measure chosen contrast targets and record failures; a colour screenshot alone is insufficient evidence.
- **Define the tested envelope explicitly:** record floor/device/view/run counts, plan dimensions and file sizes, evidence volume, concurrent sessions, browser/OS versions, device class and network conditions. Identify which design tasks and which field tasks run on each device class. Mixed-device field support alone does not promise that every complex drawing task is optimized for a phone.
- **Demonstrate preservation and conflict behaviour:** verify acknowledged saves after reload and in another session; preserve independent edits; expose same-record conflicts; retain open-page pending input during a failed online write; avoid duplicate evidence on retry; prevent undo from overwriting later work; produce exports from a coherent saved snapshot. An interrupted online write is a failure-recovery check, not an offline-workflow commitment.
- **Measure named operations:** distinguish visible response, server-confirmed save, peer update, upload completion, calculation completion and export completion. Define start/end points and repeat under the recorded envelope. Proposed durations and maximum counts must be labelled product targets until measured, not represented as established browser limits or vendor performance.

Acceptance should report the tested build, environment, fixtures, outcomes, measured timings and remaining defects against the selected targets. Passing these focused checks is not WCAG certification, a full accessibility evaluation, proof of production scalability, or a claim of loss prevention outside the exercised scenarios. No new compliance obligation or mandatory approval gate is introduced.
