## Intent

**Problem:** Criterion 21 is about what a real redeploy does to a real Worker's secrets; unit tests with fakes cannot show it, and HKDF and AES-GCM have not been seen on Cloudflare. Spec 6's deploy command also relies on how the pinned Wrangler and Cloudflare behave (the secret list's output, failed and non-interactive secret commands, how long replies differ after a secret put) and on restore paths that only its fakes have run (orchestrator ruling, 2026-11-23, from spec 6).

**Approach:** A script in `site-studio/deploy/acceptance/two-step.mjs`, run from Kevin's workstation with Wrangler signed in to the test account, drives the real deploy command, Wrangler's secret commands and the deployed API, records each check's outcome without secrets, and deletes every Worker it made. Patterned on story 1.3's spec 4.

## Boundaries & Constraints

**Always:**
- Safety (finding 13), before the first deploy: run `wrangler whoami` and stop unless the account named is "PhySec Site Studio"; pass that account's id as `CLOUDFLARE_ACCOUNT_ID` to every Wrangler call; run `wrangler secret list --name <w>` for `site-studio-test-15a`, `site-studio-test-15b` and `site-studio-test-15c` and stop unless all three answer not found (15c added by orchestrator ruling, 2026-11-23, from spec 6).
- Workers and what each is for (orchestrator ruling, 2026-11-23, from spec 6):
  - `site-studio-test-15a`: checks 1 to 5 and 8 to 14 (the installation with a stored fingerprint).
  - `site-studio-test-15b`: checks 6 and 7 (a second installation given 15a's key).
  - `site-studio-test-15c`: only the fallback of check 10, a name that should not exist; it is never deployed on purpose.
- Workers deployed with `npm run deploy:cloudflare -- --name <worker>`; all three names deleted with `wrangler delete --name <w> --force` in a `finally`, also after a failure, whether or not the script thinks the Worker exists, and then checked gone (`wrangler secret list` answers not found for each).
- The script reads the deploy command's output only to take the set-up code and the key into memory; it prints neither, writes neither to a file, and records only "printed once: yes/no". The administrator's password and every key the script makes (the wrong keys of checks 13 and 14) are generated by the script and kept only in memory; every key is given to Wrangler and to the deploy command only on standard input or in `SITE_SURVEY_DEPLOYMENT_KEY` in the child's environment, never on a command line.
- `wrangler tail` is read as `--format json` into memory only; the script keeps each event's outcome and exception names and never prints or writes raw events (finding 13). Captured Wrangler output is kept in memory; the record holds only what each check names (lengths, exit codes, yes/no, times, secret names).
- Execution order: 1, 9, 2, 3, 4, 5, 6, 7, 8, 13, 14 (which includes 11 and 12), 10, then cleanup. Check 13 runs before 14 because 14's settling rests on it.
- Checks (pass column fixed before the run):
  1. First deploy of 15a: exactly one "Deployment key" line; `wrangler secret list` shows `DEPLOYMENT_KEY`.
  2. Set-up with the printed code; an administrator turns on two-step verification through the API with a code computed from the start reply's secret; confirm answers 10 codes; the key-state route answers `{ fingerprint: "stored", key: "matches" }`.
  3. Redeploy 15a: no "Deployment key" line, the "kept" line, the secret list still holds `DEPLOYMENT_KEY` (criteria 21, 22).
  4. After the redeploy: sign-in with the password answers `{ secondStep: true }`; a fresh code (the next step) signs in (criterion 21).
  5. A recovery code signs in once and is refused the second time.
  6. Deploy 15b with `SITE_SURVEY_DEPLOYMENT_KEY` set to 15a's key: no key printed, the "supplied" line, the secret list holds it (criterion 13).
  7. Record (finding 12): when, after 15b's deploy command starts, the public key-state route on 15b first answers 200; and whether any platform error for HKDF or AES-GCM appeared in the tail outcomes during checks 2 to 5.
  8. Optional (finding 20, D-20 as amended): Kevin may check on his iPhone whether the second step's code field brings up the numeric keypad and the code autofill suggestion. He may decline; the story does not wait on it. So that no password the script holds is ever shown, the step uses a separate account: if Kevin takes it, he types into the terminal (hidden input, kept in memory) a throwaway password he makes up; the script invites `phone-check@example.test` as a standard user, accepts the invitation with that password and turns two-step verification on for it through the API; Kevin then signs in on his phone at 15a's address with that email and password, reaches the second step and records what he sees. Nothing secret is recorded. (Amended 2026-11-23 by the spec-writing session: as first written the step needed the administrator's password on the phone, which the script never shows.)
  9. `wrangler secret list --name site-studio-test-15a --format json`, standard output and standard error captured separately (orchestrator ruling, 2026-11-23, from spec 6; spec 6 review rows 8, 21, 44). Records: whether standard output, trimmed, is exactly one JSON array (yes/no), the byte length of anything else on standard output, and whether anything was written to standard error (yes/no, length). Pass: standard output is only the JSON array; any warning is on standard error. Spec 6's command parses the first JSON array of standard output, so a fail here goes back to the orchestrator.
  10. A failed `secret put` and a failed `secret delete` exit non-zero (orchestrator ruling, 2026-11-23, from spec 6). Ways, safest first:
      - put: `wrangler secret put "ACCEPTANCE INVALID NAME" --name site-studio-test-15a` with a throwaway value on standard input (a name with a space, which the API should refuse). If it exits 0, the script records that and tries the fallback: a put to `site-studio-test-15c`, a Worker that does not exist. Wrangler may offer to create a Worker for a secret put; with no terminal it may create one, so the script then lists 15c and records whether it now exists (it is deleted at the end either way).
      - delete: `wrangler secret delete ACCEPTANCE_ABSENT_SECRET --name site-studio-test-15a` with empty piped standard input (a secret that does not exist). If it exits 0, the fallback is a delete on `site-studio-test-15c` (after the put fallback, only if 15c does not exist).
      Records: each command's exit code and which way was used. Pass: a non-zero exit for each. If no safe way gives one, the check records "not shown" for that command, and the run goes on; the orchestrator decides.
  11. `wrangler secret delete DEPLOYMENT_KEY --name site-studio-test-15a` with empty piped standard input and a 60-second time limit, as the first step of check 14 (a) (orchestrator ruling, 2026-11-23, from spec 6; spec 6 review rows 30, 46: the pinned Wrangler has no `--force` and asks only on a terminal). Records: exit code, whether it ended within the limit, whether `DEPLOYMENT_KEY` is absent from the next list. Pass: exit 0 without waiting for input, and absent from the next list. The deploy command's own delete in check 14 (a) is checked the same way.
  12. A newly put key appears in the next run's secret list (orchestrator ruling, 2026-11-23, from spec 6). Records, yes/no, after check 1's generated key, after check 6's supplied key and after check 14 (b)'s restored key: the next `wrangler secret list` holds `DEPLOYMENT_KEY`. Pass: yes each time.
  13. How long key-state replies differ after a `secret put` (orchestrator ruling, 2026-11-23, from spec 6; spec 6 review row 41). On 15a, whose fingerprint is stored, the script makes at least four puts of `DEPLOYMENT_KEY` with `wrangler secret put` on standard input, alternating a wrong key made in memory and the original: wrong, original, wrong, original (so it ends with the original). From the moment each put returns it polls the public `GET /api/v1/deployment-key/state` every 3 seconds for 180 seconds; the final value is the `key` of the replies in the last 60 seconds (they must all agree, else the put is recorded as "not settled"); records the time of the last reply that differs from the final value (0 when none differs), and the count of replies. Pass: under 60 seconds after every put. If any put's differing replies last 60 seconds or longer, or one does not settle, the run records it, skips check 14, cleans up and stops for the orchestrator before the story is finished: spec 6's 60-second margin then has to change.
  14. The deploy command's restore paths, run for real on 15a (fingerprint stored, the original key in place after check 13), with keys made by the script and kept in memory (orchestrator ruling, 2026-11-23, from spec 6):
      - (a) The Worker's key is deleted (check 11) to stand for a lost key. The command is run with a wrong key in `SITE_SURVEY_DEPLOYMENT_KEY`. Pass: it prints the "Checking the deployment key" line, settles on `mismatch`, deletes the key again, prints the "not the original … removed from the Worker again" line and exits 1; the next list holds no `DEPLOYMENT_KEY`.
      - (b) The command is run with the original key supplied. Pass: it settles on `matches`, prints the "supplied" line and exits 0; the next list holds the key (check 12); a code of a later step for the administrator set up in check 2 signs in.
      - (c) A wrong key is put in the Worker by hand (`wrangler secret put` on standard input), then the command is run with the original supplied. Pass: no put and no delete by the command (the next list still holds a key and the key-state route still settles on `mismatch`), it prints the "Worker already has a deployment key, and it is not the one …" line with the manual `wrangler secret delete` command naming `site-studio-test-15a`, and exits 1.
      - (d) Records for (a), (b) and (c): the time from the "Checking" line to the command's exit. Pass: each between 60 and 180 seconds.
- Results go into this file's Run record and `deferred-work.md` gets an entry for anything not met; nothing secret in either.
- Not in this run (stays deferred in `deferred-work.md`): operator documentation of the deploy command's key (spec 6 review row 16).

**Ask First:** before the first Wrangler call of each run; before any rerun that deploys again; before continuing after check 13 fails (the run stops there by rule).

**Never:** another Cloudflare account; a Worker left running; a key, code, password or cookie value in any file, log or message, or on a command line; `sprint-status.yaml`.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Wrong account | `whoami` names another account | nothing deployed | stop |
| Leftover Worker | 15a, 15b or 15c exists | nothing deployed | stop |
| First deploy | new Worker | key printed once, secret listed | stop, delete Workers |
| Redeploy | key present | no key printed; listed unchanged | stop, delete Workers |
| Sign-in after redeploy | two-step set up before | second step, then signed in | record and stop |
| Supplied key | second Worker | used, not printed | record |
| List output | `secret list --format json` | only the array on standard output | record; fail goes to the orchestrator |
| Failed put / delete | invalid name; absent secret; fallback 15c | non-zero exits, or "not shown" | record; 15c deleted at the end |
| Delete without a terminal | empty piped standard input | exits 0 within 60 s; key gone from the next list | record |
| Replies after a put | four puts, polled 180 s each | last differing reply under 60 s each time | 60 s or more, or not settled: record, skip 14, clean up, stop for the orchestrator |
| Restore, wrong key | key deleted; wrong key supplied | settles `mismatch`; deleted again; exit 1; no key listed | record |
| Restore, original | original supplied | settles `matches`; exit 0; code sign-in works | record |
| Wrong key in the Worker | wrong key put by hand; original supplied | nothing changed; manual-delete line; exit 1 | record |
| Settle time | (a), (b), (c) | 60 to 180 s each | record |
| Phone check | Kevin declines | skipped; recorded as declined | N/A |
| Cleanup | any outcome | all three names deleted; `wrangler secret list` for each answers not found | report |
