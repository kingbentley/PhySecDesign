## Intent

**Problem:** Criterion 21 is about what a real redeploy does to a real Worker's secrets; unit tests with fakes cannot show it, and HKDF and AES-GCM have not been seen on Cloudflare.

**Approach:** A script in `site-studio/deploy/acceptance/two-step.mjs`, run from Kevin's workstation with Wrangler signed in to the test account, drives the real deploy command and the deployed API, records each check's outcome without secrets, and deletes every Worker it made. Patterned on story 1.3's spec 4.

## Boundaries & Constraints

**Always:**
- Safety (finding 13), before the first deploy: run `wrangler whoami` and stop unless the account named is "PhySec Site Studio"; pass that account's id as `CLOUDFLARE_ACCOUNT_ID` to every Wrangler call; run `wrangler secret list --name <w>` for `site-studio-test-15a` and `site-studio-test-15b` and stop unless both answer not found.
- Workers deployed with `npm run deploy:cloudflare -- --name <worker>`; deleted with `wrangler delete --name <w> --force` in a `finally`, also after a failure, and then checked gone (`wrangler secret list` answers not found for each).
- The script reads the deploy command's output only to take the set-up code and the key into memory; it prints neither, writes neither to a file, and records only "printed once: yes/no". The administrator's password is generated by the script and kept only in memory.
- `wrangler tail` is read as `--format json` into memory only; the script keeps each event's outcome and exception names and never prints or writes raw events (finding 13).
- Checks (pass column fixed before the run):
  1. First deploy of 15a: exactly one "Deployment key" line; `wrangler secret list` shows `DEPLOYMENT_KEY`.
  2. Set-up with the printed code; an administrator turns on two-step verification through the API with a code computed from the start reply's secret; confirm answers 10 codes; the key-state route answers `{ fingerprint: "stored", key: "matches" }`.
  3. Redeploy 15a: no "Deployment key" line, the "kept" line, the secret list still holds `DEPLOYMENT_KEY` (criteria 21, 22).
  4. After the redeploy: sign-in with the password answers `{ secondStep: true }`; a fresh code (the next step) signs in (criterion 21).
  5. A recovery code signs in once and is refused the second time.
  6. Deploy 15b with `SITE_SURVEY_DEPLOYMENT_KEY` set to 15a's key: no key printed, the "supplied" line, the secret list holds it (criterion 13).
  7. Record (finding 12): when, after 15b's deploy command starts, the public key-state route on 15b first answers 200; and whether any platform error for HKDF or AES-GCM appeared in the tail outcomes during checks 2 to 5.
  8. Optional (finding 20, D-20 as amended): Kevin may, on his iPhone, open 15a's sign-in page, reach the second step, and record whether the numeric keypad and the code autofill suggestion appear. He may decline; the story does not wait on it. Nothing secret is recorded.
- Results go into this file's Run record and `deferred-work.md` gets an entry for anything not met; nothing secret in either.

**Ask First:** before the first Wrangler call of each run; before any rerun that deploys again.

**Never:** another Cloudflare account; a Worker left running; a key, code, password or cookie value in any file, log or message; `sprint-status.yaml`.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Wrong account | `whoami` names another account | nothing deployed | stop |
| Leftover Worker | 15a or 15b exists | nothing deployed | stop |
| First deploy | new Worker | key printed once, secret listed | stop, delete Workers |
| Redeploy | key present | no key printed; listed unchanged | stop, delete Workers |
| Sign-in after redeploy | two-step set up before | second step, then signed in | record and stop |
| Supplied key | second Worker | used, not printed | record |
| Cleanup | any outcome | both Workers deleted; `wrangler secret list` for each answers not found | report |
