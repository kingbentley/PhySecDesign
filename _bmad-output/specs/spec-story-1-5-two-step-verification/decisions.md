1. **D-1 Where the two-step controls live in this story** (Claude, accepted on Kevin's instruction, 2026-11-22). "My account" in the account menu opens a My account dialog holding only a "Two-step verification" section (state, remaining recovery codes, turn on, fresh codes, turn off); story 1.6 adds profile, password and sessions to the same dialog. Reason: the story needs the controls and "the account page shows how many recovery codes remain"; this puts them where story 1.6 expects them without taking its scope.
   - Rejected: the whole My account page now; a "Two-step verification" menu item moved by story 1.6.
2. **D-2 What carries the pending sign-in token** (Claude, accepted on Kevin's instruction, 2026-11-22). Its own cookie `__Host-ssd-p-<identifier>`, 32 random bytes, `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`, `Max-Age=300`; the second-step body carries only the code. Reason: scripts cannot read it, and "bound to that browser" is the browser's own cookie jar.
   - Rejected: the token in the sign-in reply, held by the page, plus a binding cookie.
3. **D-3 Reload and one pending sign-in per browser** (Claude, accepted on Kevin's instruction, 2026-11-22). A reload during the second step shows the sign-in page again; a new sign-in attempt discards the pending token the browser presents, before its wait check, and every sign-in reply other than `{ secondStep: true }` clears the pending cookie (amended for finding 23). Reason: the 5-minute token makes the loss small.
   - Rejected: the session read reports a pending second step.
4. **D-4 How second-step failures count** (Claude, accepted on Kevin's instruction, 2026-11-22; CA-15; deferred-work item on the marker count). A correct password for a two-step account clears nothing; each wrong code or recovery code raises the email count, the marker count (if the password attempt carried a usable marker) and the request address's count, as a wrong password does; a correct one clears the email and marker counts and its password attempt's address row. The second step takes the request's address (amended for finding 4). When a wrong code starts a wait the pending token is discarded and the reply is `signin_wait` with its seconds (amended for finding 3); a second step that meets a wait from any attempts discards it and answers `signin_wait`. A marker in its own wait is treated as absent (finding 36). Reason: a known password must not buy fresh guesses; this gives 4 code guesses from a clear count, then none until it clears (the review's arithmetic: about 0.1% a day).
   - Rejected: the correct password clears the counts and the second step starts fresh.
5. **D-5 Re-checks on account actions** (Claude, accepted on Kevin's instruction, 2026-11-22). The password given to turn on, turn off or make fresh codes, and the code given for fresh codes, are checked through the hash queue and counted like a sign-in attempt for that account's email, the browser's marker and the known address, meeting the same wait; the confirm code at set-up is not counted. Key availability is checked before counting for turn on and fresh codes (amended for finding 14), and counts clear only when the whole action succeeds (amended for finding 19). Reason: CA-13 guards a session left open.
   - Rejected: not counted.
6. **D-6 TOTP details** (Claude, accepted on Kevin's instruction, 2026-11-22; within CA-12). HMAC-SHA-1, a 20-byte random secret, base32 without padding in groups of four; a code is accepted only for a time step later than the last one accepted for that account, at set-up and sign-in, the last step re-read inside the deciding step (finding 9). Reason: some apps ignore the algorithm; the last-step rule makes reuse fail across the three accepted steps.
   - Rejected: HMAC-SHA-256.

8. **D-8 How the QR code is drawn** (Claude, accepted on Kevin's instruction, 2026-11-22). 9. **D-9 Recovery code format and storage** (Claude, accepted on Kevin's instruction, 2026-11-22; within CA-11). 16 characters from Crockford's base32 in lower case (80 bits), shown as four groups of four joined by hyphens; entry ignores case, spaces and hyphens; stored as SHA-256 of the normalised code; a used code's row is deleted. CA-55 and standing rule 14's "at least 20 random characters" concern the administrator recovery code of story 1.13, not these codes; AD-12's sentence is to be clarified at the next architecture edit (`deferred-work.md`; finding 37). Reason: 50 bits under a fast hash can be searched offline; 80 bits cannot.
   - Rejected: 10 characters; scrypt per code.

14. **D-14 The deployment key and the cipher** (Claude, accepted on Kevin's instruction, 2026-11-22). The key is 32 random bytes, base64url without padding, in the Worker secret `DEPLOYMENT_KEY`; HKDF-SHA-256 derives an AES-256-GCM key and a fingerprint; values are stored as `v1.<IV>.<ciphertext>` with associated data naming the record. A value that does not parse counts as no key (finding 30). Reason: Web Crypto provides both on Workers and workerd; associated data stops a ciphertext moving between accounts.
    - Rejected: AES-CBC with HMAC; a crypto library.
15. **D-15 When the fingerprint is stored and what a mismatch does** (Claude, accepted on Kevin's instruction, 2026-11-22; CA-52). Stored with the first encrypted value, the insert re-checked in the deciding step (finding 18); every encrypted read and write compares it; on a mismatch, or a missing key once a fingerprint is stored, set-up and code checks are refused `deployment_key_mismatch`, the two-step state read reports it, and the object logs one line once per start (no key material); recovery codes (hashes) and turning off (a delete) keep working. Deleting a ciphertext is not reading or writing an encrypted value (finding 38). Reason: nothing to protect before a value exists, and people keep a way in.
    - Rejected: stored at first start; refusing every two-step action.

17. **D-17 The deploy command's key handling** (Claude, accepted on Kevin's instruction, 2026-11-22; amended for findings 1, 2, 10, 11, 28 and 29). Every run first says to run one deploy at a time for a Worker. Deploy, check the Worker name, then list the Worker's secrets (captured output; the operator's key removed from every Wrangler child's environment). When the key is absent, poll the key state. With nothing stored: a supplied key is put; otherwise a key is generated and printed before it is put, and a failed put says the printed key may have been stored. With a fingerprint stored: a supplied key is put and then confirmed against the fingerprint by polling the key state (`matches` goes on; `mismatch` or no answer exits 1); with none supplied the command stops. Then story 1.2's set-up-code steps. The operator's key comes from `SITE_SURVEY_DEPLOYMENT_KEY`, checked for its form before deploying, never printed. Two deploys at once remain a race, recorded for Epic 9's workflow in `deferred-work.md`. Reason: the key stays off the command line, can never be lost unseen, and a lost Worker key can be restored with the original only. Orchestrator ruling, 2026-11-22 (Claude, on Kevin's instruction), after spec 6's build review: a supplied key this run put that the key state then reports as `mismatch` is deleted again (`wrangler secret delete`), the only key the command ever deletes, so that the rerun its message asks for works; a supplied key while one is in the list is checked against the stored fingerprint (a mismatch changes nothing and exits 1 with the manual delete command), and a failed supplied put says the key may have been stored. A second orchestrator ruling the same day (Claude, on Kevin's instruction, on stale replies from Worker copies still on an earlier version): those two decisions rest only on a settled answer, the same `matches` or `mismatch` on every readable reply over 60 continuous seconds (at least 21 replies), within 180 seconds, else "not confirmed" and nothing deleted. Orchestrator ruling of 2026-11-24 (Claude, accepted on Kevin's instruction; Kevin may overrule), after CodeRabbit's review of pull request 13 (round 1, finding 1): the key state is read from an address while secrets go to the Worker Wrangler named, so before any key step (list, put, delete, key-state read) a `--url` is accepted only when its host equals, without regard to case and exactly (no suffix matching), a host Wrangler reported for this deploy: an `https://` target's host, a custom domain's host, or a route pattern's host with no wildcard; otherwise the command stops after the deploy with one error line (`wording.md`), exit 1, nothing listed, put or deleted and no set-up code. Known cost: an installation reached only through an address Wrangler does not report (a wildcard route, a separate proxy host) cannot use `--url` for the key steps (`deferred-work.md`, story 9.12). **Builder's narrowings in the same round, built first and then confirmed by the orchestrator after reading the round's commit (ruling of 2026-11-24, Claude, accepted on Kevin's instruction):** (1) a route counts only when it covers the whole host (`host/*`), since the key-state route sits at the origin's root and a route limited to a path leaves it to something else (found by the round's review layers); (2) a `--url` with an explicit port is refused; (3) a settled answer must complete within the 180 seconds: a reply that completes later decides nothing (CodeRabbit finding 40, reading "within 180 seconds" as the reply's completion).
    - Rejected: a `--deployment-key-file <path>` option. Rejected on 2026-11-24: reading the key state always from Wrangler's own address (breaks custom-domain-only installations); leaving `--url` unchecked and documenting it.
18. **D-18 The public key-state route** (Claude, accepted on Kevin's instruction, 2026-11-22; amended for findings 2 and 10 as ruled). `GET /api/v1/deployment-key/state` answers `{ fingerprint: "none" | "stored", key: "none" | "present" | "matches" | "mismatch" }`: `key` is `none` when the Worker has no usable key, `present` when it has one and nothing is stored, and `matches` or `mismatch` only when a fingerprint is stored. It never answers the fingerprint or anything derived from the key; the review's option of publishing the Worker key's fingerprint was not taken. The deploy command generates no key while encrypted values exist without one, and confirms a restored key. **What a stranger learns:** whether anyone on the installation has ever turned on two-step verification (`stored`), and whether the installation's key is configured and matches. Neither helps an attacker: no key material, fingerprint or account is revealed; a mismatch makes code checks fail closed (two-step still blocks sign-in, and only a person's own recovery codes get in); the route is read-only and needs no counting; and the same facts follow from behaviour a stranger cannot reach without an account anyway. Reason: generating a new key over stored ciphertext would make every stored secret unreadable at once (for example after a rollback that drops the secret, AD-21).
    - Rejected: no such route; the Worker key's fingerprint in the reply.
