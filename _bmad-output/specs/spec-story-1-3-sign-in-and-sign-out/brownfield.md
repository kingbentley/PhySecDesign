## Implementation notes

- **Order of a sign-in attempt** (mirrors set-up):
  1. Check the origin and the app header.
  2. Validate the input against the schema.
  3. Ask the installation object to count the attempt by email key and by address, or refuse with a wait. With a valid marker for that email, only the address can impose a wait (CA-44). The object answers with the stored hash, or a stand-in signal for an unknown email or inactive account, and a one-time ticket. Both answers take the same object path.
  4. In the Worker, verify `normalisePassword(password)` against the stored hash or the stand-in hash.
  5. Ask the object to complete: with the ticket and the outcome. On success it removes this attempt from both counts, clears the email's count, ends any session the browser presented, stores the new session's hash, and returns the account's name and the token's expiry. On failure the counts already raised stay.
  6. Reply with `Set-Cookie` for the session (and the marker on success).
- **Timing parity (CA-58).** Both cases run the same steps: one object call, one scrypt hash with the same parameters, one completing call. Measure from the HTTP client. 20 refusals of one email would hit its own wait after 5, so the test seeds several accounts directly through `runInDurableObject`, sends each attempt with a distinct `CF-Connecting-IP`, and spreads attempts so no wait applies. A hash takes about 0.4 s, so 40 refusals need a test timeout of several minutes.
- **Simultaneous attempts.** Counting and the ticket happen in one synchronous object step, so of 25 attempts sent at once for one email, 5 get tickets and 20 get the wait. The server test sends them with `Promise.all`; the deployed check sends them over several connections.
- **Memory (D-5).** Five checked attempts at once mean five 128 MiB scrypt hashes, above the 128 MB Worker instance limit if they share an isolate. A per-isolate queue keeps one at a time.
- **Cookie in local runs.** `wrangler dev` and the Vite dev server serve `http://127.0.0.1` or `http://localhost`. The server always sets `Secure`. Chromium keeps such cookies on those hosts; WebKit is unconfirmed; spec 3 checks it first and moves the local test servers to HTTPS if WebKit drops the cookie (D-10).
- **Browser-test budget.** Each local server has one address bucket (`unknown`). More than 19 failed sign-ins within 15 minutes in one project's run would make every later sign-in wait. Keep the failure tests few and ordered, or give the wait test its own server.
- **Installation identifier (D-1).** The Worker needs the identifier to name the cookie before it can read a session. It costs one object read per request, which the gate already makes (AD-17); an isolate may keep it, as it never changes.
- **No route resets state.** Tests get fresh installations from fresh servers or fresh object names, as in story 1.2.
- **Unchanged parts.** The four Sites files and their outputs, the dev-only review middleware, and the node tests from before story 1.2 stay as they are.
