## Implementation notes

- **Order of a sign-in attempt** (mirrors set-up):
  1. Check the origin and the app header.
  2. Validate the input against the schema.
  3. Ask the installation object to count the attempt by email key and by address, or refuse with a wait. With a valid marker for that email, only the address can impose a wait (CA-44). The object answers with the stored hash, or a stand-in signal for an unknown email or inactive account, the identifier, and a one-time ticket. The ticket records the account or "stand-in", the email key, the address key, the marker flag, the stored hash's identity and the presented session's hash (A-1, E-22). Both answers take the same object path.
  4. In the Worker, verify `normalisePassword(password)` against the stored hash or the stand-in, through the queue.
  5. Ask the object to complete with the ticket and the outcome only. A stand-in ticket is a failure whatever the outcome. On success it re-checks that the account is active with the same stored hash, removes this attempt from the address count, clears the email's count, ends the presented session, stores the new session's hash, and returns the account's name. On failure the counts already raised stay.
  6. Reply with the session cookie and the marker, appended as separate `Set-Cookie` headers.
- **Timing parity (CA-58).** Both cases run the same steps: one object call, one queued scrypt hash with the same parameters, one completing call. Interleave known and unknown attempts after a warm-up; seed several accounts through `runInDurableObject` and send each attempt with a distinct `CF-Connecting-IP` so no wait applies; set the file's own timeout (40 hashes of about 0.4 s). Assert each median at least 150 ms, so the clock is shown to see the hash: whether workerd's clock inside the test isolate advances across scrypt is unverified (V-2). Keep the file from running beside other scrypt-heavy files, or record that it does. Show once that skipping the stand-in check fails the test, and record it in the spec 2 file.
- **Simultaneous attempts.** Counting and the ticket happen in one synchronous object step, so of 25 attempts sent at once for one email, 5 get tickets and 20 get the wait. Tests send them with no cookies (A-6): the server test with `Promise.all`, the deployed check over 25 separate connections with `node:https` agents and keep-alive off.
- **Memory (D-5).** The claim that five 128 MiB hashes in one isolate exceed the 128 MB Worker limit is unproven: story 1.2 spec 4 ran two at once without error and could not show they overlapped. Recording it on Cloudflare, or dropping it, is held with the queue's bound (H-7).
- **Cookie in local runs.** `wrangler dev` serves `http://127.0.0.1`; `npm run dev` serves `http://localhost`. The server always sets `Secure`. Spec 3 checks the real `__Host-` session cookie in both Playwright projects on `127.0.0.1`, and Kevin's local Chrome run on `localhost`, and records both (A-16).
- **Browser-test budget.** Each local server has one address bucket (`unknown`). The wait test uses an email with no account and its own `CF-Connecting-IP`; tests that produce failures stay under 20 per server (V-15).
- **Installation identifier (D-1).** No isolate keeps it (A-18, E-12): the Worker passes every cookie with the session prefix and the object answers with its identifier, so a re-created object or a test's fresh storage never meets a stale name. Whether the vitest plugin resets object storage between tests is unverified; tests use their own object names as story 1.2's do.
- **No route resets state.** Tests get fresh installations from fresh servers or fresh object names, as in story 1.2.
- **Unchanged parts.** The four Sites files and their outputs, the dev-only review middleware, and the node tests from before story 1.2 stay as they are.
